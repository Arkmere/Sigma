# Architecture

## Stack selection

Sigma uses a TypeScript static application. TypeScript provides explicit boundaries without introducing a framework dependency before the product model exists. The app builds to static browser assets that can be served locally and later wrapped by Capacitor or another native shell for phone deployment.

TypeScript is a project-local development dependency pinned in `package-lock.json`; the npm workflow does not rely on a globally installed `tsc`.

Alternatives considered: React Native/Expo offers stronger native deployment but adds mobile build complexity before the data model exists; React/Vite remains a reasonable later choice when the product requires richer component composition; Next.js would add server concepts Sigma does not need for a local-first demo.

## Layers and structure

- `src/app/content.ts`: route identifiers, navigation metadata and page copy for the Ticket 1 shell.
- `src/app/app.ts`: top-level route/theme state, render selection and event-binding orchestration.
- `src/app/ui`: focused shell, profile, record, status, form-action and shared HTML modules.
- `src/app/ui/anatomy-navigator.ts`: supplementary path-driven visual controller whose family-resolved whole-body and detail assets map presentation geometry only to existing semantic anatomy paths.
- `src/domain/model.ts`: schema-4 canonical entities, optional fact references, non-destructive correction and current-measurement selection.
- `src/domain/canonical-facts.ts`: immutable canonical creation/discovery registry and controlled anatomy metadata, independent of stored records.
- `src/domain/anatomy-discovery.ts`: deterministic semantic hierarchy and exact-path results derived from canonical `anatomyPath`; eligibility intersects canonical measurements with the existing guidance and illustration registries.
- `src/domain/measurement-guidance.ts`: local structured guidance referenced by canonical physical definitions, including placeholder-only illustration and future tutorial metadata.
- `src/domain/sharing.ts`: deterministic sharing scopes, access and grant authority.
- `src/domain/service.ts`: profile, record, history, search and export operations.
- `src/domain/taxonomy.ts`: initial browse taxonomy.
- `src/conversion`: typed results, central units/aliases, dimensional semantics, discrete sizing tables, conservative ring helpers and isolated source metadata.
- `src/data/repository.ts`: explicit load-status and versioned persistence boundary.
- `src/data/migrations.ts`: runtime schema validation, referential integrity and migration dispatch.
- `src/lib/preferences.ts` and `src/lib/entitlement.ts`: separate local UI/demo preferences.
- `src/styles.css`: semantic design tokens, responsive layout and component styles.
- `src/manifest.json`: PWA manifest; `src/assets/icons/`: generated installable-app icons.
- `scripts/build.mjs`: cross-platform static asset preparation after TypeScript compilation, including build-ID cache-busting and PWA asset copying.
- `scripts/dev.mjs`: cross-platform build-then-serve development command; prints a LAN URL for phone testing.
- `scripts/generate-icons.mjs`: one-off dependency-free PNG icon generator (Node's built-in `zlib` only), not part of the build pipeline.
- `.github/workflows/deploy.yml`: builds and deploys `dist/` to GitHub Pages on push to `main`.
- `test`: Node test files for deterministic utilities, DOM-like shell interaction and source-level guardrails.

## State and routing

The shell controller has six top-level destinations. Profile/record creation and Family stages are transient disclosures rather than routes. Family renders only the selected operational stage. Record search restores focus and caret after the dependency-free full render. Notices are action-owned transient state: the immediate action render preserves or replaces them, while ordinary route and focused-stage navigation clears stale messages.

Measurement guidance uses one escaping renderer. Creation swaps canonical-ID-addressed panels in place, preserving entered values and search focus; saved editable and read-only cards reuse the same renderer after normal access filtering. Guidance is never inferred from a label and never enters `SigmaData`.

Semantic anatomy discovery is an optional in-form presentation layer. It derives child regions and exact-path facts from the registry rather than maintaining UI fact lists. Region panels and the supplementary visual switch in place, so navigation does not recreate the form or discard entered values; fact selection updates the existing canonical select and invokes its authoritative default-unit and guidance update. The browser exists only inside the existing manage-authorized creation surface. Its open/current-path state is transient, and presentation-family selection is not an input to discovery.

Ticket 6F2 adds a visual controller beside those semantic panels. It hydrates the existing family-specific `body-front` asset through the unchanged safe standalone loader, then layers four generous application-owned hit regions for Head and neck, Torso, Upper limbs and Lower limbs. Geometry is family-specific presentation metadata because native viewBoxes and proportions differ; every geometry entry resolves directly to the corresponding first-level `AnatomyPath` and contains no fact IDs. Visual and DOM region controls call the same navigation function and share selected-state derivation. The SVG is a pointer/touch enhancement hidden from the accessibility tree; semantic buttons remain authoritative for keyboard and assistive technology. Hit/selected state is transient and absent from schema 4 and preferences.

Ticket 6F3 extends that controller without adding navigation state. The active semantic `AnatomyPath` selects `upper-limb-front`, `hand-palm`, `finger-detail`, `lower-limb-front`, or `foot-top` through the existing family asset registry; only actual semantic children receive visual geometry. The normalized detail assets permit common generous Hand, Fingers and Foot geometry across Neutral, Masculine and Feminine, while the differently proportioned whole-body views retain family-specific geometry. Fingers and Foot are contextual terminal visuals whose measurements remain semantic DOM actions. Replacing only the visual stage preserves the record form, and back navigation naturally restores the parent visual from the same path. Incomplete geometry fails closed to the complete semantic browser. No fact IDs, guidance metadata, persistence, schema fields, or focusable SVG controls are introduced.

## Sources and contextual permissions

`src/sources` owns the typed nine-source registry, explicit stable external-field allowlist, mixed local demo adapter, fail-closed evaluation and confirmed import translation for physical measurements and standard sizes. Candidate creation requires both global field allowlisting and the resolved source's field and record-kind capabilities. Only `demo` sources use the external import boundary; `future` sources return `source_not_available`, while live manual entry continues through its dedicated service workflow. Raw source identity, item ID, device, confidence and derivation remain untrusted until runtime evaluation produces a canonical-ready candidate. The measurement-and-sizing device is the sole operational external demo and permits height, weight, waist circumference, foot length, shoe size and ring size. Brand-fit import remains unsupported.

Ticket 7A makes each allowed external field an explicit mapping to `src/domain/canonical-facts.ts`; source definitions retain only additional field, record-kind, availability and narrower unit/system policy. Accepted and revalidated candidates carry `canonicalFactId` and derive label, category and measurement semantics from that registry. Confirmed physical imports append provenance-bearing values to an existing measurement with the same profile and canonical ID, while canonical standard sizes retain their designed coexistence semantics. Historical records without canonical IDs are not reinterpreted or migrated.

`src/permissions` owns five permission kinds and the complete explanation contract. Decisions are simulated (`not_requested`, `demo_granted`, `demo_denied`) and stored separately at `sigma.permissionDemo.v1`; they never enter `SigmaData` or backup exports. No real platform API is called. Canonical import mutation still passes through `SigmaService` and its Ticket 4A owner/manager rule.

The shell was split into content metadata and rendering code during Ticket 1A. This is a small maintainability improvement that avoids one monolithic controller without prematurely creating a large framework-style folder hierarchy.

## Local persistence

Theme and anatomy-family presentation preferences are stored separately through `src/lib/preferences.ts`. Canonical schema-4 data uses `LocalStorageRepository`, a typed versioned adapter over browser localStorage. Domain and UI code do not access preference storage keys directly. The service saves after each authorized mutation and can export a complete versioned JSON snapshot. Conversion operations are read-only service methods derived from the current valid value at render time and are never persisted.

Canonical standard-size and brand/product update methods validate category and sizing system against the attached canonical definition before mutation. Fixed category and standard-size label metadata are derived from the registry; permitted system changes and record-specific value, notes, brand and product fields remain editable. Consequently a successful canonical edit remains valid under an immediate repository reload. Custom records remain outside these canonical restrictions.

Loads produce `empty`, `ok`, `corrupt`, or `unsupported_version`. A missing, non-numeric or non-finite version is corrupt; an unknown finite numeric version is unsupported. Versions 1 through 3 are validated and migrated; schema 4 validates scoped ID uniqueness, referential and authorization invariants, correction metadata and optional canonical references including fixed measurement and standard-size labels. Record grants resolve by kind, ID and owner. Schema-3 canonical mapping also requires compatible stored units and suppresses same-profile physical-fact collisions. Corrupt/unsupported raw storage is preserved and both mutations and backup export remain blocked until explicit reset.

LocalStorage keeps the static foundation dependency-free and makes deterministic persistence tests straightforward. Its trade-offs are synchronous access, browser-specific capacity/retention and no Sigma-provided encryption. The repository interface allows a future IndexedDB adapter without changing domain operations.

## Theme architecture

The app stores a theme preference of `system`, `light` or `dark`, resolves it against `prefers-color-scheme`, and applies `data-theme` to the document. It separately stores an anatomy illustration preference of `neutral`, `masculine` or `feminine` under `sigma.anatomyFamily`; missing or invalid values resolve to Neutral. CSS semantic tokens implement the visual system.

## Build and development architecture

`npm run build` runs local TypeScript compilation and then executes `scripts/build.mjs`, which uses Node built-in filesystem APIs to create `dist/`, copy static assets and write production `index.html`. It does not use Unix `cp`, Bash or Python. It also generates a per-build timestamp ID and stamps `?v=<id>` onto every local asset reference in `index.html` and `manifest.json`, so a static host without custom cache-control headers still serves fresh assets after each deploy.

`npm run dev` executes `scripts/dev.mjs`. The script builds first, then serves the freshly generated `dist/` directory with Node's built-in HTTP module. It does not currently watch files. It prints a LAN-reachable URL (via `node:os` `networkInterfaces`) alongside `localhost` so the running build can be opened from a phone on the same network for functional testing; this does not by itself provide the secure context required for installable "Add to Home Screen" behaviour.

`scripts/generate-icons.mjs` is a one-off script (not part of the build pipeline) that hand-encodes PNG icons using only Node's built-in `zlib.deflateSync`, keeping icon generation dependency-free. Its output is committed as static assets under `src/assets/icons/` and copied into `dist/` by `scripts/build.mjs` like any other asset.

`.github/workflows/deploy.yml` builds and deploys `dist/` to GitHub Pages on every push to `main` (`npm ci && npm test && npm run build`, then `actions/upload-pages-artifact` and `actions/deploy-pages`). This is the mechanism for getting a real HTTPS URL to test PWA installation on a physical phone; it requires Pages to be configured with "GitHub Actions" as its source once in repository Settings.

## Testing architecture

Node built-in tests cover profile and record creation, measurement history/current-value rules, provenance, profile isolation, search, export shape, persistence reload and DOM-like route/record rendering. The UI harness is deliberately lightweight and is not a full browser engine.

## Linting status

No lint command exists after Ticket 1A because the previous command was misleading: it duplicated type checking. A real linter should be added later before documenting `npm run lint` again.

## Future seams

- Source adapters: health platforms, devices, camera and third-party sources must pass allowlisted measurement data into the future record engine.
- Permission service: future platform permissions must be mediated by a pre-permission explanation flow.
- Conversion expansion: add permitted, versioned table rows or categories through registries without moving formulas or tables into UI code.
- Sharing/consent boundary: connections, grants, revocation and auditability must be independent of Family membership.
- Entitlements: future paid unlock state must not become a payment SDK dependency.

## Cloud and telemetry

No backend, hosted database, authentication provider, analytics, telemetry, advertising SDK or crash uploader is included.

Reason: the picker and card were flagged as the least discoverable and most information-dense parts of the app; trade-off: card disclosure summaries changed shape, so tests asserting exact prior summary text were updated alongside the implementation.
49. **Post-audit Family/Sources navigation pass:** `app.ts` gained real hash-based routing (`parseHash`/`hashFor`, plus a `hashchange` listener) covering all six top-level routes and the four non-overview Family stages. It is guarded behind `typeof window !== 'undefined'` so the Node test harness — which has no `window`/`location` — takes the exact same direct state-mutation path it always has; only real browsers get URL sync, deep links and back/forward support. Reason: `familyView` and `route` were previously two variables a human had to keep in sync by hand, and the app had no history entries at all, so back/forward silently left the app. Family stages gained a direct switcher between each other (not just back to Overview) via a new `.stage-tabs` CSS class — deliberately not reusing `.record-tabs`, which is hidden under a 620px breakpoint for an unrelated reason (the record-type tabs it was built for); giving the switcher its own class avoided silently breaking Family navigation on exactly the phone widths this product targets. Sources gained scroll/focus management on its action-triggered panels (`#permission-explanation`, `#import-candidates`, `#source-status`), reusing the existing `tabindex="-1"` + `.focus()` idiom from `#record-form-panel` rather than introducing a new pattern.
50. **PWA installability — no service worker:** Sigma is installable via `src/manifest.json` plus `index.html` head tags (manifest link, apple touch icon, `mobile-web-app-capable`/`apple-mobile-web-app-capable`), matching the pattern used for the product owner's other installable-PWA project. Icons are generated once by `scripts/generate-icons.mjs` using only Node's built-in `zlib`, keeping the dependency-free build intact. Reason: Sigma already has zero runtime network dependency (localStorage-only), so a service worker and offline cache would add complexity without adding capability; "installable and app-like" was the actual requirement, not "works offline from a cold cache." Trade-off: without a service worker, the very first load of a given build still requires network access (or a previously cached page from ordinary HTTP caching) — there is no explicit offline-first guarantee. The app shell (`.app-shell`, `.content` in `styles.css`) now fills the viewport with `overflow: hidden` and only the content region scrolls, to avoid the page-level bounce/rubber-band that reads as "a website" rather than an installed app. `.github/workflows/deploy.yml` deploys `dist/` to GitHub Pages on push to `main` for real-device HTTPS testing; enabling Pages itself is a one-time manual repository-settings step.
51. **Ticket 9 real deletion — schema 5:** `SigmaService` gains `deleteMeasurementValue`/`deleteMeasurement`/`deleteStandardSize`/`deleteBrandFit`/`deleteProfile`, the first true removals (`.splice`/array-reassignment) this codebase has ever done — every prior "undo" (`revokeGrant`, `disconnect`, `correctMeasurementValue`) was a status flip that kept the row forever. Reason: deletion was an explicit, named product requirement ("update, amend, delete, convert"), and every profile-ID reference in the schema was previously required to resolve to an existing profile with no exception, so adding real deletion is a genuine schema change, not a pure code change. Design: profile-ID references split into subject/party fields (record `profileId`, grant owner/recipient, connection parties, membership `profileId`, `managedByProfileIds`) which deletion always cascades to clean up and which may never dangle, versus historical "who did this" attribution fields (`grantedByProfileId`, `revokedByProfileId`, `createdByProfileId`, `addedByProfileId`, `correction.correctedByProfileId`) which schema 5 deliberately tolerates dangling, since the record they're attached to may still be owned by someone who exists — including loosening the grant/revocation authority-alignment checks specifically when that actor no longer resolves to any profile, so deleting a manager doesn't retroactively invalidate grants they made while they still had authority. `deleteMeasurementValue` refuses to remove a record's only remaining value (delete the whole record instead) — matched in the UI by simply not rendering the delete control rather than surfacing a rejected-action error. Trade-off: `data/migrations.ts`'s validators now take an `allowDanglingAttribution` parameter threaded through three function layers, adding real complexity to the most safety-critical file in the codebase; this was verified against the actual validation code line-by-line, not a summary, given how expensive a wrong migration is to discover after the fact.
52. **Ticket 10 encrypted fit-card exchange — schema 6:** cross-device sharing does not go through any server — `src/exchange/crypto.ts` encrypts a JSON export (`FitCardPayload`: sender identity, scope, and the scoped measurements/standard-sizes/brand-fits at export time) with a passphrase-derived AES-GCM 256 key (PBKDF2, 250,000 iterations, SHA-256, random salt/IV per export) into a downloadable `EncryptedFitCardFile` (`src/exchange/model.ts`), using only Web Crypto (`crypto.subtle`) — no dependency, and the same code path runs unmodified under Node 20+ in tests and in the browser. Reason: the actual stated use case is "see a family member's size so you can buy them a gift," not live profile comparison, so a one-shot signed/encrypted export-file-then-import model was chosen over any kind of persistent link, account, or sync relationship — the recipient explicitly imports a snapshot into a new, separate `ImportedFitCard` record (`profileId`-free: it carries `senderProfileId`/`senderDisplayName` as plain display data, not a party reference) rather than the sender's records ever appearing to merge into the recipient's own profile data. `SigmaService.exportFitCardPayload` reuses the existing `canManageProfile`/`scopeCovers` authorization exactly as sharing grants do — export is not a new access-control concept, just a new output format for data the actor could already see. `importFitCard`/`deleteFitCard` are plain local mutations with no authorization beyond `ensureWritable()`, since an imported card belongs entirely to the importing device/actor. `data/migrations.ts`'s `validateImportedFitCards` deliberately does not require `scope.recordId` (when scope is record-typed) to resolve against any locally-known record, since the record it names lived on the sender's device, not this one — the embedded measurement/standard-size/brand-fit objects are still validated with the existing `validMeasurementValue`/`validStandardSize`/`validBrandFit` functions. Trade-off: passphrases are shared out-of-band (message, call, in person) with no key-exchange protocol; a lost passphrase makes that specific export file permanently unrecoverable, matching the product's local-first, no-recovery posture elsewhere (e.g. corrupt-storage state) rather than introducing the first server-mediated recovery path in the app.
